== Demo personas

This demo uses two SSO (Keycloak) personas. Both use the common password `{password}`. Use these credentials for the OpenShift console, GitLab, Dev Spaces, and Developer Hub.

* **`{dev_user}`** — Developer persona ("Dave Developer"). Use this when demonstrating the developer experience: DevSpaces, writing code, pushing commits, viewing pipeline results.
* **`{pe_user}`** — Platform engineer persona ("Paul Platform Engineer"). Use this when demonstrating platform configuration: DevSpaces operator, Service Mesh, production deployments.

When signing into the OpenShift console, will first be prompted to select a login type. Use the `developers` identity provider for the developer and platform engineer personas and enter one of the above usernames and password. If you need to login as the cluster admin, use the built-in `htpasswd` option with the admin credentials (`admin`/`{admin_password}`).

[TIP]
====
To avoid constant sign-out/sign-in noise during the demo, keep each persona logged in using a separate browser. For example, use Chrome for the developer persona and Firefox for the platform engineer persona (or use an incognito/private window for the second persona). This lets you switch between personas instantly by switching browser windows.
====

Other services (SonarQube, Argo CD, Vault) require their own admin credentials — see the access details below.

== Running `oc` commands

In some places, it's easiest to use `oc` to fetch dynamic data like passwords or URLs. You can run `oc` commands via the OpenShift console's built-in terminal. To open the console terminal, click the "_>" icon in the top right of the console header. This opens a terminal pane with a command prompt that has `oc` already configured and logged in as your user.

== Environment namespaces

Throughout the modules you'll work on applications belonging to a fictitious company named Parasol. The following lists explain each application namespace and why it exists. Notice that we use new namespaces in each module to avoid conflicts and start from a clean slate, or to separate personal developer environments from shared environments.

=== Section 1: Foundational application platform

* **`parasol-insurance-dev`** — Development environment for the Parasol application. Receives deployments from the CI/CD pipeline on every code push.
* **`parasol-insurance-prod`** — Production environment. Deployments are controlled through GitOps (Argo CD) with manual approval gates via GitLab merge requests.
* **`parasol-insurance-build`** — Contains Tekton pipeline definitions, EventListeners, and build tasks. Pipeline runs execute here, not in the dev/prod namespaces.

=== Section 2: Secured supply chain

* **`parasol-insurance-secured-dev`** — Development environment with the full secure supply chain — ACS vulnerability scanning, image signing (TAS), SBOM generation, and SLSA attestation via Tekton Chains.
* **`parasol-insurance-secured-prod`** — Secured production environment. Promotion requires two manual gates: a code merge request approval + tag creation, and a GitOps merge request approval.
* **`parasol-insurance-secured-build`** — Secured build pipeline namespace. Contains the main EventListener and pipelines for both feature branch builds and production tag promotions.

=== Per-user namespaces

* **`<username>-devspaces`** — Auto-provisioned by DevSpaces for each developer's cloud IDE workspaces and associated PVCs.
* **`parasol-insurance-secured-<username>`** — Created via the Developer Hub "Parasol Insurance Secured Development" golden path template. Each developer gets an isolated namespace with its own pipeline and Argo CD application for their feature branch.

== Demo application

The demo application is the **Parasol Insurance** web application, a Quarkus-based microservices application that handles policy management, claims processing, and customer interactions. Parasol migrated this application from a legacy Java EE platform to Quarkus on OpenShift using the Migration Toolkit for Applications (MTA).

In section 1 (foundational), the application has two environments:

* **Dev**: `{parasol_dev_ns}` namespace — parasol-insurance-{parasol_dev_ns}.{subdomain}
* **Prod**: `{parasol_prod_ns}` namespace — parasol-insurance-{parasol_prod_ns}.{subdomain}

The Tekton pipeline and build resources are in the `{parasol_build_ns}` namespace.

In Section 2, the application and all its components are registered in the Red Hat Developer Hub catalog as a "system" with linked components (frontend, backend, Kafka, database). They land in parasol-insurance-secured-dev and parasol-insurance-secured-prod namespaces, with a secure build pipeline that includes ACS, TAS, and Tekton Chains but you don't necessarily need to visit these namespaces, as RHDH acts as the 'single pane of glass', for visualizing topologies, pipelines, argo apps, and more.

In Section 3, the application is extended with an AI-enhanced component that consumes the LLM endpoint and processes business data from Kafka.

== Post-provisioning fix-ups (run once per instance)

The `ocp4-adv-app-platform-demo` catalog item is provisioned as-is; this enablement lab does not control its bootstrap. A few defects in the provisioned instance break the Section 2 flow for every group, so the instructor (or each group's driver during Module 2) runs one script from the OpenShift console **Web Terminal** (`>_` icon, top right) as cluster admin:

[source,bash,role="copypaste"]
----
curl -fsSL https://raw.githubusercontent.com/rhpds/openshift-advanced-platform-demo/main/scripts/post-provision.sh | bash
----

To include the optional layers (Connectivity Link, the Developer Hub plugins, observability, the Kiali tab; about 35 minutes more), and when the lab is served from a fork, set the variables first:

[source,bash,role="copypaste"]
----
export REPO_RAW=https://raw.githubusercontent.com/rhpds/openshift-advanced-platform-demo/main   # or your fork
export WITH_RHCL=1 WITH_RHDH_PLUGINS=1 WITH_OBSERVABILITY=1 WITH_KIALI_PLUGIN=1
bash <(curl -fsSL $REPO_RAW/scripts/post-provision.sh)
bash <(curl -fsSL $REPO_RAW/scripts/validate-instance.sh)
----

`validate-instance.sh` is read-only and prints PASS/FAIL for every layer, including one end-to-end trace (gateway, Authorino, Limitador, backend hop); run it before the session on each instance. The Postman collection in `tests/postman/` (seven folders, with a runbook) exercises the same paths from a laptop.

It takes about 2 minutes, or up to 8 minutes the first time when the `1.0` promotion pipeline has to run. It is idempotent, so re-running it is safe. What it fixes, and why:

**Optional: Connectivity Link layer (Module 3, Part 1b).** The demo does not ship Red Hat Connectivity Link. Three additional scripts install it on top of the instance without touching the Parasol application: `scripts/rhcl/install.sh` (operator, control plane, console plugin), `scripts/rhcl/gateway.sh` (the `parasol-gateway` gateway of class `istio`, exposed through a Route) and `scripts/rhcl/parasol-api.sh` (the `parasol-api` HTTPRoute, the API-key `AuthPolicy`, the `RateLimitPolicy` and the `partner1` key). Run them in that order from the Web Terminal; each one verifies itself and has a `delete` mode. Skip Part 1b on instances without this layer. Two more scripts extend it: `scripts/rhcl/api-product.sh` publishes the claims API as a Connectivity Link **API Product** with gold/silver/bronze plans, which appears in the Developer Hub "Connectivity Link → API Products" page (needs the Kuadrant Developer Hub plugins, `scripts/rhdh-kuadrant/apply.sh` followed by `db-pool.sh`); and `scripts/rhcl/llm-gateway.sh` puts the external LLM endpoint of Section 3 behind the same gateway at `http://llm.parasol-gateway.svc/v1`, with a platform key per team (sent as a normal `Authorization: Bearer` header, so any OpenAI client works unchanged; the provider key is injected by the gateway from a Secret in `kuadrant-system` and never appears in a route, a policy or the application) and a `TokenRateLimitPolicy` counted from `usage.total_tokens`. `scripts/rhcl/llm-switch-app.sh <user> <branch>` points one Section 3 application at it through Vault (`secrets/litellm/gateway`) and one line in its GitOps repo; `revert` puts it back. `post-provision.sh` runs all of this with `WITH_RHCL=1 WITH_RHDH_PLUGINS=1`.

**Optional: observability layer (Module 3, Part 2).** `scripts/observability/install-operators.sh` (Tempo, OpenTelemetry and Grafana operators), `tracing.sh` (Tempo, an OpenTelemetry collector, the Istio tracing provider with one `Telemetry` per ambient namespace, Limitador and Authorino spans, Kiali reading from Tempo) and `grafana.sh` (Grafana with the Thanos and Tempo datasources, ten dashboards, Grafana links in Kiali). `traces-api.sh` publishes Tempo's query API through the gateway for the end-to-end test. `scripts/rhcl/mcp-gateway.sh` (run with `WITH_RHCL=1`) publishes Developer Hub's MCP server through the gateway with platform keys, and `scripts/rhdh-kuadrant/kiali.sh` (`WITH_KIALI_PLUGIN=1`) adds the **Service Mesh** tab to Developer Hub through a second, token-authenticated Kiali instance (the demo's Kiali keeps its OpenShift login). **Extra personas.** `scripts/users/create-persona.sh <user> <first> <last> <email> <dev|pe> [avatar.svg]` creates a developer or platform-engineer persona mirroring `dev1` / `pe1` across Keycloak, OpenShift, GitLab and Developer Hub, with an avatar in the Developer Hub header; `scripts/users/create-superuser.sh` creates an all-access one. `scripts/rhdh-kuadrant/lightspeed-prompts.sh` replaces the Lightspeed suggestion cards. == Pre-demo checklist

[WARNING]
====
**Resurrected clusters:** If you stopped a running demo cluster and later restarted it, two things can break. The `post-provision.sh` script above repairs both; the manual steps follow.

**Developer Hub login fails with an error 500.** The RHDH pod usually starts before Keycloak and the ingress VIP are back, and its OIDC discovery stays stuck even after they recover. Restart it:

[source,bash,role="copypaste"]
----
oc rollout restart deployment/backstage-developer-hub -n rhdh
----

**Parasol application pods crash-loop.** The Istio ambient service mesh may fail to re-establish `HBONE` tunnels to existing pods. This causes the Parasol application to fail to connect to its PostgreSQL database, and pipelines that attempt to restart the application will fail. If you encounter this, restart the database and application pods in the affected namespaces by running the following commands in the OpenShift console terminal:

[source,bash,role="copypaste"]
----
for ns in $(oc get deployment -A -l app=parasol-db -o jsonpath='{range .items[*]}{.metadata.namespace}{"\n"}{end}'); do
  echo "Restarting parasol-db in $ns"
  oc rollout restart deployment -l app=parasol-db -n $ns
done
for ns in $(oc get deployment -A -l app=parasol-db -o jsonpath='{range .items[*]}{.metadata.namespace}{"\n"}{end}'); do
  echo "Waiting for parasol-db in $ns"
  oc rollout status deployment -l app=parasol-db -n $ns --timeout=60s -w
done
oc get deployment -A -l 'app in (parasol-insurance,parasol-insurance-secured)' -o jsonpath='{range .items[*]}{.metadata.namespace}{" "}{.metadata.name}{"\n"}{end}' | while read ns name; do
  echo "Restarting $name in $ns"
  oc rollout restart deployment/$name -n $ns
done
----

The commands will take about 1-2 minutes to complete. Wait for all rollouts to finish before proceeding with the demo.
